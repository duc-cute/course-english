10. SWOT, rủi ro & anti-pattern

Anti-pattern: “PDF Viewer + bài tập”

Lesson = HTML dài + file đính kèm, không quiz/audio/checkpoint → HS chỉ scroll và đánh dấu xong.

Phòng tránh: block QUIZ bắt buộc; audio checkpoint; rule hoàn thành (ví dụ ≥80% quiz đúng); progress có nghĩa trên server.

Điểm mạnh

  • Lesson Player + 10 loại câu exercise + progress server
  • HS UI Vibrant Scholar (home, path, vocab, profile)
  • LinguistAI chat + sinh câu từ PDF/DOCX (schema gọn + parallel batch)
  • Students Need Support + notification in-app

Điểm yếu / rủi ro

  • Assignment module chưa có
  • XP/streak/badge chưa lưu BE
  • VIDEO/AUDIO block editor chưa đủ
  • RabbitMQ/Redis chưa bật — scale sau

16.3.1 Last activity — inactiveDays

lastActivityAt = MAX(
  lesson_reading_progress.updated_at,
  lesson_practice_attempts.completed_at
) trên mọi lesson PUBLISHED thuộc lớp HS

Nếu chưa có activity → lastActivityAt = enrollment.joined_at

inactiveDays = số ngày (ChronoUnit.DAYS) từ lastActivityAt đến now
Rule +50 khi inactiveDays > 7

16.3.2 Missing assignments — missingCount (cần lessons.due_at)

GV gán Hạn nộp khi publish/sửa lesson. Lesson không có due_at → không tính missing.

eligible = lesson PUBLISHED + due_at IS NOT NULL + thuộc lớp HS ACTIVE

OVERDUE (thiếu / quá hạn):
  due_at < now AND không có attempt với passed = true
  → missingCount++, risk +30 (một lần nếu có ≥1 OVERDUE)

UPCOMING (chưa làm, còn hạn):
  due_at >= now AND chưa passed
  → KHÔNG tính risk, KHÔNG vào missingCount
  → chỉ hiện trong popup View Profile

16.3.3 Average score — avgScorePercent

Với mỗi lesson có ít nhất 1 attempt: lấy best score_percent
avgScorePercent = trung bình các best score
(Lesson chưa có attempt → bỏ qua, không tính 0)

Rule +25 khi avgScorePercent < 60

16.3.4 Score trend — scoreTrendPercent

Sắp xếp lesson theo thời gian attempt gần nhất
recentAvg  = TB best score của 3 bài gần nhất (có điểm)
previousAvg = TB best score của 3 bài ngay trước đó
scoreTrendPercent = recentAvg - previousAvg   (âm = tụt)

Rule +20 khi scoreTrendPercent <= -15

17.2.3 Giải pháp hiện tại — lý do đổi cách làm

A. Tối giản output schema (giảm ~15–20% output tokens)

Trước: Model phải sinh tempId, selected, promptLang, difficulty, choiceKey, displayOrder… cho mỗi câu và mỗi đáp án.

Sau: Model chỉ sinh nội dung học thuật — questionType, promptText, explanation, choices[{choiceText, correct}] (và contentJson cho TF / Fill / Reading).

Backend gắn metadata: AiQuestionGenResultValidator + normalize() trên từng handler → tempId (q1, q2…), selected=true, promptLang, difficulty, choiceKey a/b/c/d, blank id b1/b2, Reading sq1…

Lý do: Mỗi ký tự output = thời gian sinh; metadata là quy ước cố định của LMS — không cần LLM «sáng tạo».

B. Parallel batch v2 (giảm wall-clock)

Điều kiện bật: ≥2 loại câu và tổng ≥ AI_QUESTION_GEN_BATCH_MIN_QUESTIONS (mặc định 10). Ngược lại → single-shot + stream.

Cách chia: AiQuestionBatchPlanner chia đều (vd. 20 câu MCQ+Fill → 10+10). Mỗi nhóm = 1 request OpenRouter, system prompt chỉ 1 loại + example tối giản của loại đó.

Song song: CompletableFuture trên aiOpenRouterExecutor (max 2 concurrent). Wall-clock ≈ thời gian nhóm chậm nhất, không phải tổng.

Chấp nhận trade-off: Excerpt tài liệu lặp mỗi batch — input token tăng nhưng Flash input rẻ; đổi lại tiết kiệm phút chờ của GV.

Partial success: Task vẫn DONE nếu ≥1 batch thành công; câu lỗi giữ validationErrors[]; meta.summaryMessage (vd. «Đã sinh 18/20 câu hợp lệ») hiện banner ở bước Xem trước.

Lý do đổi so với v1: Per-type prompt mỏng hơn + example vẫn có + validate/merge an toàn + không fail cả task vì 1–2 câu skeleton.
